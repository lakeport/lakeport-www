# Always release the frontend first

When a feature spans both client and server, teams usually ask: *"Do we deploy the backend first or the frontend first?"*

In Lakeport, our default answer is **always release the frontend first**, with new UI paths and outbound commands gated behind server-advertised capabilities that start **off**.

At first glance that sounds backwards. Why ship frontend code for a backend feature that is not turned on yet? Walk through what happens during an ordinary rolling deploy and the reason becomes clear.

## Why "backend first" still bites you in rolling deploys

Suppose you are adding **Instant Escrow Release** (`Version.v2` + capability `instant_release`). If you deploy the new backend and turn the behavior on immediately while clients are only halfway rolled out, or if you deploy an ungated frontend that assumes every server speaks `v2`:

1. **Load-balancer split brain.** During a 10-minute rolling deploy, half of your backend pods run the old binary and half run the new one. An ungated client hits a new pod on page load, then hits an old pod on its next `POST` and gets a `400` or `404`.
2. **Offline outbox replay.** A mobile user queues an `instantRelease` action while on `v2`, walks into an elevator, and reconnects after you rolled the backend back to fix an unrelated memory leak. Without a capability gate on replay, the outbox hammers the rolled-back server with frames it cannot parse.
3. **Painful rollbacks.** If the backend migration misbehaves and clients are already assuming the new contract unconditionally, rolling back the server breaks active client sessions.

## The four-step frontend-first rollout

Instead, separate **shipping code** from **turning behavior on**:

1. **Step 1: Ship the frontend first (gate closed).** The new client understands both `Version.v1` and `Version.v2`, knows how to render the Instant Release button, and knows how to encode `V2.ClientFrame.instantRelease`. Because the current production server only advertises `versions = [v1], capabilities = []`, the client negotiates `v1`, hides the Instant Release button, and blocks `instantRelease` at the command gate. User-visible change: zero.
2. **Step 2: Deploy the dual-version server (capability still off).** Roll out the backend binary supporting both `v1` and `v2`, advertising `versions = [v1, v2], capabilities = []`. Updated clients shift cleanly to `v2` baseline framing while older cached clients keep speaking `v1` without error.
3. **Step 3: Enable the capability advertisement.** Once all backend instances are healthy, flip server config to advertise `capabilities = [instant_release]`. On their next capability refresh, clients reveal the Instant Release UI and `permitsV2Command` opens.
4. **Step 4: Roll back by withdrawing the capability (if needed).** If metrics spike, remove `instant_release` from `GET /api/capabilities`. Clients hide the control and hold or downgrade unnegotiated commands without requiring an emergency frontend redeploy or mobile App Store review.

## Guard the command boundary as well as the JSX

Hiding a button in your `.lp` view is good ergonomics, yet it is **not** a safety boundary. A keyboard shortcut, a stale timer callback, or an offline outbox flush can still fire an action when the button is not on screen.

Always check `permitsV2Command` (or `permitsEncodedFrame`) inside your pure reducer before emitting an outbound `EffectReq`:

```lean title="Guarding both direct clicks and outbox retries"
def sendV2 (ad : Option Advertisement) (nextId : Nat) (connId : Nat)
    (cmd : Wire.V2.ClientFrame) : Option EffectReq :=
  if permitsV2Command ad cmd then
    some (.wsSend nextId connId (Wire.V2.encodeReq cmd))
  else
    none
```

Now you can state a two-line theorem in your `*Laws.lean` file that holds regardless of what your UI components do:

```lean title="Kernel-checked rollout gate"
theorem unnegotiated_instant_never_emits (ad : Option Advertisement)
    (hNoCap : permitsV2Command ad (.instantRelease cid cents) = false) :
    sendV2 ad nextId connId (.instantRelease cid cents) = none := by
  simp [sendV2, hNoCap]
```

<Callout kind="warning" title="When backend-first is required">
There is one classic exception: **additive server-side tolerances** before a client stops sending a legacy field, or adding a database index before a client queries it. Even then, the rule is the same underlying principle: *deploy tolerances and gates first, activate new traffic last.*
</Callout>
