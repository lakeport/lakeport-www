# Pure core, explicit effects, and Lean proofs

Teams hearing about formal verification for the first time usually worry about two failure modes:

1. *"Will every CSS tweak require a three-hour Coq proof?"*
2. *"What stops someone from proving a toy helper function while the real app runs completely different code?"*

Both worries are valid. Lakeport's architecture is designed specifically to avoid both traps.

## Prove invariants of your domain, not pixel coordinates

You never write theorems about margin widths or hover colors. Instead, split your `src/` folder along a clean seam:

- **Domain modules (`src/*.lean`)** hold your `State`, `Action`, `WellFormed : State -> Prop`, and pure `step : State -> Action -> State × List EffectReq`.
- **Law modules (`src/*Laws.lean`)** import your domain modules and prove `theorem` declarations about `step`.
- **View modules (`src/*.lp`)** import your domain modules and render `State` to `StyledView`.

Because `App.lp` calls the exact `step` function that `StateLaws.lean` proves theorems about, **there is no gap between the specification model and the executed reducer**. At the same time, you can redesign `App.lp` and `app.css` ten times a day without touching a single proof.

## A concrete conservation invariant

Here is a simplified escrow reducer where money sits in one of three buckets: `available`, `held`, or `released`. A bug that duplicates or loses cents during a retry is catastrophic.

```lean title="src/Escrow.lean"
structure Ledger where
  available : Nat := 10000
  held : Nat := 0
  released : Nat := 0
  inFlight : Bool := false
  deriving DecidableEq, Repr

def TotalCents (l : Ledger) : Nat :=
  l.available + l.held + l.released

inductive Action where
  | reserve (cents : Nat)
  | settleHeld
  | socketDropped
  deriving DecidableEq

def step (l : Ledger) : Action -> Ledger
  | .reserve cents =>
    if !l.inFlight && cents <= l.available then
      { l with available := l.available - cents, held := l.held + cents, inFlight := true }
    else l
  | .settleHeld =>
    { l with held := 0, released := l.released + l.held, inFlight := false }
  | .socketDropped =>
    { l with inFlight := true }
```

Notice `.socketDropped`: when a WebSocket closes mid-flight before the server acknowledges whether the reserve succeeded, we **keep `inFlight := true`** (uncertain delivery) until reconciliation completes rather than blindly clearing the lock and allowing a duplicate debit.

Now look at the conservation theorem in `EscrowLaws.lean`:

```lean title="src/EscrowLaws.lean"
import Escrow

namespace Escrow.Laws
open Escrow

theorem step_conserves_cents (l : Ledger) (a : Action) :
    TotalCents (step l a) = TotalCents l := by
  cases a with
  | reserve cents =>
    unfold step
    split
    · rename_i hOk
      simp only [Bool.and_eq_true, decide_eq_true_eq] at hOk
      simp [TotalCents]
      omega
    · rfl
  | settleHeld =>
    simp [step, TotalCents]
    omega
  | socketDropped =>
    rfl

end Escrow.Laws
```

Lean's built-in `omega` tactic discharges the natural-number subtraction (`cents <= l.available` implies `(available - cents) + (held + cents) + released = available + held + released`) automatically. Notice what happens if you remove `cents <= l.available` from `step`: `Nat` subtraction truncates at zero, `omega` refuses the goal, and Lean points right at the underflow bug.

## Always write one productive witness theorem

Safety theorems ("nothing bad happens") have a classic blind spot: a reducer that ignores every click and returns `l` unchanged trivially conserves cents!

Pair every safety invariant with at least one **productive witness theorem** showing that valid user sequences actually reach the intended state:

```lean title="Productive witness in EscrowLaws.lean"
theorem reserve_then_settle_releases :
    let l0 : Ledger := {}
    let l1 := step l0 (.reserve 2500)
    let l2 := step l1 .settleHeld
    l2.available = 7500 ∧ l2.held = 0 ∧ l2.released = 2500 := by
  decide
```

If an overzealous capability gate accidentally rejects every command, `reserve_then_settle_releases` breaks immediately.

## Rules for [proof-only, 0 B C] modules

Lakeport classifies a `.lean` module as `[proof-only, 0 B C]` and omits its C translation unit from native and WebAssembly linking when two conditions hold:

1. No runtime module reachable from `App.lp` imports it.
2. The file declares `theorem` or `lemma` items and **zero** computational definitions (`def`, `abbrev`, `structure`, `inductive`, `class`, `instance`, `opaque`, `axiom`, or `@[extern]`).

<Callout kind="tip" title="Where to put Prop predicates">
Put `Prop` definitions like `def WellFormed (s : State) : Prop := ...` inside your domain file (`State.lean`), not inside `StateLaws.lean`. Because `WellFormed` returns `Prop`, Lean erases it to zero bytes inside `State.lean`, and `StateLaws.lean` stays strictly `theorem`-only so Lakeport drops the entire law module from the C/Wasm link!
</Callout>

## What Lakeport audits on release builds

When you run `lakeport check` or `lakeport build web --release`, keep three rules non-negotiable:

- **`0 sorry` (`sorryAx`):** Unfinished proofs never ship.
- **`0` custom `axiom` declarations:** No invented axioms hiding unproved assumptions.
- **`0 Lean.ofReduceBool` (`native_decide`):** Use kernel-checked `decide`, `rfl`, `simp`, `cases`, and `omega` so the Lean kernel itself verifies every step without trusting native code evaluation inside the compiler.

## Naming the trust boundary honestly

We avoid marketing badges like "100% Verified" or artificial `L0-L4` assurance grades because a real system always has both proved pure code and an unproved runtime boundary. Document both sides plainly in your repo:

- **Kernel-checked:** URL round-trips (`LawfulUrlCodec`), wire frame round-trips, capability gates, conservation/well-formedness across `step`, and `MemoCell` view cache coherence.
- **Trusted computing base (tested, not kernel-proved):** Lean 4's C code generator, `clang --target=wasm32`, `boot.mjs` / `dom-renderer.mjs` (or the native GTK/AppKit/UIKit/Android shell), and the host OS/browser.
