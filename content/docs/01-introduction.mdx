# Introduction to Lakeport

Lakeport is an application framework in development, written in Lean 4 for teams building with coding agents. You write your state, reducers, routing, wire codecs, views (`.lp` TSX), and stylesheets (`.css`) in one project. Compiled Lean WebAssembly (`wasm32`) powers browser apps and static sites today, including `lakeport.dev`, while native C host shells remain in active development.

If you have built apps with Elm, Solid, or React, the mental model will feel familiar right away. Your interface is a pure function of your state:

```lean title="The Lakeport loop"
State -> StyledView Event Field
```

When someone clicks a button or types into a text field, the host shell sends an event into your Lean reducer. The reducer computes the next state and a list of outbound effects (an HTTP call, a clipboard write, a WebSocket frame). Lakeport diffs the view tree and patches only the DOM nodes that changed.

## Why Lean 4 for application code?

Most UI frameworks stop at type-checking props and JSON shapes. That catches typos, which helps in day-to-day work, yet it leaves the hardest bugs untouched: conservation of balances, offline retry ordering, stale server capabilities during a rolling deploy, and state transitions that violate an invariant five clicks deep.

Lean 4 is both a functional programming language (compiling to C with Perceus reference counting) and an interactive theorem prover. In Lakeport, those two halves live in the same file tree:

- **Your app is ordinary functional code.** You define structures, inductive sums, and `.lp` TSX components much like you would in TypeScript or Elm. You do not need to write a single proof to get a working app on screen.
- **When a rule matters, you state it as a theorem.** Because your reducer is a pure function with no hidden mutation or ambient `IO`, Lean's kernel can verify properties about the exact `step` function your users execute in WebAssembly.
- **Proofs cost zero bytes at runtime.** Every `Prop` and every `theorem` is erased before C and WebAssembly code generation. Modules that contain only theorems (`*Laws.lean`) compile to zero bytes of object code.

<Callout kind="important" title="What proofs cover (and what they do not)">
A Lean theorem proves a property of your pure model, wire codec, or reducer under explicit hypotheses and recorded axioms. It does not prove that a browser engine, operating system kernel, or remote server is bug-free. Good Lakeport code keeps the imperative host shell small and pushes real state decisions across the boundary into pure Lean.
</Callout>

## Why coding agents thrive in Lakeport

If you pair-program with coding agents, you have probably noticed failure modes that unit tests miss. An agent fixes a flaky retry test by clearing a pending flag early, or adds a wildcard `_ => pure ()` branch to silence a compiler warning. All twenty test cases pass, and then a customer gets billed twice on spotty train Wi-Fi.

Lakeport turns business constraints into compile-time walls that an agent cannot talk its way past:

1. **Exhaustive versioned contracts.** Edge handlers match every wire version without wildcard arms. An unimplemented case fails `lakeport check`.
2. **Kernel-checked invariants.** If `escrow_conserves_cents` says `available + held + released = 10000` across every action, a buggy retry patch fails to compile until the invariant holds for *all* inputs, not merely the three inputs in a test file.
3. **Banned escape hatches.** Release checks inspect the compiled Lean environment for `sorryAx` and custom axioms. An agent cannot stub out a hard proof obligation and declare victory.

## Target architecture and recorded evidence

Lakeport targets real platform primitives rather than a custom Skia canvas. We report recorded evidence separately from end-state scope, and no platform family claims a completed full-framework production gate (`G-P`) yet:

| Target | Host shell | Recorded status |
| --- | --- | --- |
| Web (SPA + SSG) | Compiled `wasm32` + DOM renderer | Active primary route (`lakeport.dev`, static pre-rendering + Wasm hydration); full-framework `G-P` open |
| Android | C / JNI + Android Views | Bounded JNI and emulator runtime probes executed; framework support not yet claimed |
| macOS, Windows, Linux | C + AppKit / Direct2D / GTK4 | Bounded runtime and headless layout probes executed; native UI support gates open |
| iOS | C + UIKit | Simulator and device cross-link probes verified; app execution and UI support pending |
