# What Lakeport is (and is not)

Lakeport is a client application framework built on Lean 4 and compiled to WebAssembly (with native desktop and mobile shells in active development). You write component views in JSX-style `.lp` files and styles in regular `.css` files, state your critical client rules in plain English, and let your coding agent maintain the Lean state logic and proofs beside them.

You do not need prior Lean experience to adopt Lakeport, and you do not need Lean on your backend.

## Where Lakeport pays off most: local-first and client-heavy apps

In a traditional server-rendered or thin CRUD web app, most business rules live on the backend inside database transactions. If a browser only renders forms and posts them to a server, proving theorems on the client buys very little.

Lakeport benefits **local-first** and client-state-heavy software more than almost any other frontend stack, because real business logic lives on the user's device:

- **Offline sync queues and outboxes:** Edits accumulate while disconnected, replay across flaky connections, and reconcile when responses arrive out of order.
- **Optimistic UI and collaborative state:** Local mutations apply immediately and must converge cleanly with server acknowledgements without duplicating or dropping items.
- **Stateful checkouts and idempotent retries:** Client retry loops must keep in-flight payment or reservation tokens locked when Wi-Fi drops mid-request.
- **Long-lived tabs and Service Worker caches:** Frontend bundles cached on a device continue talking to Go, Node, Python, or Rust backends while schemas evolve across deploys.

Whenever bugs hide in state transitions rather than pixel alignment, Lean's exhaustive pattern matching and zero-byte compile-time theorems catch mistakes that happy-path unit tests miss.

## What you read and edit vs. what your agent writes

| Concern | File type | Who typically writes it | Runtime footprint |
| --- | --- | --- | --- |
| Component markup & layout | `src/*.lp` | You or your coding agent | Lowered to `StyledView` and compiled to Wasm |
| Visual tokens & layout rules | `src/*.css` | You or your coding agent | Static `bundle.css` (and `.lpcss` for native shells) |
| Client state, JSON decoders & reducers | `src/*.lean` | Your coding agent, guided in plain English | Compiled to C11 and `wasm32` |
| Invariants & regression laws | `src/*Laws.lean` | Your coding agent via `lakeport mcp` | **0 bytes** (`[proof-only, 0 B C]`) |

## Honest platform status

Lakeport separates what is production-ready today from platform targets whose verification gates are still open:

| Target | Current status | Notes |
| --- | --- | --- |
| **Web (SSG + Wasm SPA)** | Production-ready (`● proved` / `◐ trusted`) | Pre-rendered static HTML hydrating into a single `wasm32` binary (`app_lp2.wasm`) over the `LP2` v4 ABI. |
| **Linux Desktop (GTK4 / PangoCairo)** | Experimental (`○ unknown` open gates) | Native C11 host rendering `.lpcss` flex/grid trees; full cross-platform UI gate still open. |
| **Android, iOS, macOS, Windows** | Experimental (`○ unknown` open gates) | JNI Java, Swift UIKit/AppKit, and Win32 Direct2D adapters exist in `packages/`, with bounded runtime probes rather than closed UI gates. |

<Callout kind="note" title="Four-state evidence discipline">
Throughout Lakeport and this manual, every technical claim is labeled as **proved** (checked by the Lean 4.35 kernel with `0 sorryAx`), **trusted** (compiler, browser DOM, OS), **unknown** (open platform gates or live network conditions), or **failed** (a broken draft rejected by `lakeport check`).
</Callout>

1. **Getting started:** Install the CLI, connect `lakeport mcp`, and build a verified local-first outbox step by step.
2. **Recommended patterns:** Structure pure client state, decode evolving backend JSON schemas without Lean on the server, and ship frontend-first releases across Service Worker caches.
